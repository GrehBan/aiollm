# aiollm provider

A provider is a flat package `aiollm_<name>`, published as `aiollm-<name>`,
in a repository of its own, that takes from the core only the extension API
(`aiollm/testing/extension_api.json`). The smallest worked example is the
echo provider of the test kit (`src/aiollm/testing/echo/` and
`tests/testing/test_echo_contracts.py`); the full ones are
[aiollm_openai](https://github.com/aiollm-org/aiollm_openai) and
[aiollm_anthropic](https://github.com/aiollm-org/aiollm_anthropic), whose
layout, CI and `CLAUDE.md` a new repository copies. The steps are in
`docs/guide/extending.md` and the conventions in `CLAUDE.md`. Read them
first - this skill is the order of work and the checks that make a provider
complete.

## 0. Agree first

Adding a provider adds a repository, a package and its public surface:
propose it (`change-proposal`) with what upstream offers (from its
official OpenAPI file, SDK types and API reference), the auth scheme, error
format and stream format, which shared resources it will support, and any
name the core would have to add to the extension API. Code starts on the
owner's go; the repository, its ruleset and its PyPI publisher are set up
by the owner.

## 1. What the core needs first

A name the provider must import and the extension API lacks is added to
`extension_api.json` in a core pull request first, never imported around
it. The core's `downstream` job and `tests/downstream/` list the providers
it checks; a new one is added there once its repository exists.

## 2. Repository skeleton

Copied from aiollm_openai: `pyproject.toml` (dist `aiollm-<name>`, the core
pinned to a commit, `aiollm[testing]` in the test group, the `codegen`
group, ruff's isort section for the core), `src/aiollm_<name>/__meta__.py`,
`.github/workflows/` (`tests.yml`, `core-master.yml`, `publish.yml`,
`upstream.yml`), `CHANGES/`, `CLAUDE.md`, `CONTRIBUTING.md` and its skills.

## 3. Package (`src/aiollm_<name>/`)

1. `api.py`: `BaseAPI(base_url, version)` and `PROVIDER: Final =
   Provider("<name>")` (an open value: nothing changes in the core).
2. `resolver.py`: `BaseErrorResolver` subclass with `provider = PROVIDER`,
   `error_statuses` (in-band code/type → status), `get_error_code` or
   `classify_status` for codes such as quota vs rate limit; in-band failures
   are never transient.
3. `client.py`: module-level `session_factory = SessionFactory(AiohttpSession,
   auth_factory=..., api=..., error_resolver=...)`, and a `BaseProviderClient`
   subclass with `provider`, `session_factory`, `api_key_env`, `auth_headers`
   and each resource as `name = bind_resource(Resource[...], Adapter)`
   (`adapter_factory=` for an adapter with options, read from the client);
   `__init__` types `**session_kwargs`, keeps the adapter options and calls
   `super().__init__()`, which builds adapters before the session. The
   generation adapter has `with_options` with the provider's options
   `TypedDict` (`types/options.py`), and the client binds
   `GenerationResource[Raw, Event, Options]`.
4. `__init__.py` re-exports the client (the one `__init__` allowed to import a
   transport), sorted `__all__`.

## 4. First endpoints

Types and request parameters generated by aiollm-codegen from the pinned
upstream schema (`scripts/generate_types.py`), the snapshot of the wire
contracts (`tests/contracts/`, checked with `aiollm.testing.wire`), the
hand-written method classes and adapters; the providers' own
`ai-api-endpoint` skill is the order of work.

## 5. Tests

- `conftest.py` loads `aiollm.testing.plugin` and names the provider's key
  in `provider_key_envs`.
- `test_generation_contract.py`, `test_files_contract.py` (when it has a
  Files API: a `BaseFilesAdapter` bound as `files`) and
  `test_client_contract.py`: a case and a subclass of `GenerationContract`,
  `FilesContract` and `ClientContract` of `aiollm.testing.contract`. A
  scenario that would need a branch for the provider gets a case field in
  the core instead; the scenarios never name a provider.
- `test_extension_api.py`: `check_extension_api("aiollm_<name>") == []`.
- `test_client.py` keeps only what is the provider's own;
  `typing/check_public_api.py` and `public_api.json` as in the two
  providers.

## 6. Docs, release

In the core: a `docs/guide/providers.md` section, a reference page and its
nav entry, a column of `docs/unification.md` for every shared field and error
case, the README feature list, and the provider in the `lint and types`,
`downstream` and `docs.yml` installs. In the provider: its README and
`ai-api-release` fragment. Then `definition-of-done`. Report in Russian.
